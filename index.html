🔧 트러블슈팅 1 — KIS API 초당 요청 제한
문제
보유 자산이 늘자 스케줄러가 KIS API를 몰아 호출해 EGW00201(초당 거래건수 초과) 발생.
원인
자산 1건당 현재가·등락률을 API 2번으로 조회했고, 순회 사이 지연이 없어 자산 수에 비례해 순간 호출이 증가.
해결
응답에 현재가·등락률이 함께 온다는 점을 이용해 호출을 1회로 병합, 순회에 Thread.sleep(300) 추가, 갱신 주기 8초→12초.
성과
10종목 이상 등록해도 초당 제한 오류 없이 갱신.
🔧 트러블슈팅 2 — Refresh Token 재발급 시 동일 토큰
문제
인증 통합 테스트 중, 로그인 직후 바로 재발급하면 이전과 완전히 동일한 JWT가 나오는 경우를 발견.
원인
Refresh Token 페이로드를 subject·발급시각(ms)·만료로만 구성해, 같은 밀리초에 발급되면 HMAC 서명 결과까지 동일. 재발급마다 새 토큰으로 바꾸는 로테이션 전제가 깨짐.
해결
jti(랜덤 UUID) claim을 추가해 같은 밀리초라도 토큰이 항상 달라지게 수정.
🔧 트러블슈팅 3 — 자산 규모가 커지자 드러난 캐시 전략의 한계
문제
자산을 50개 넘게 등록한 계정에서 GET /api/portfolio가 500(EGW00201, 초당 거래건수 초과)을 내고, 오류를 막은 뒤엔 조회가 매번 몇 초~수십 초씩 걸림. 자산이 적을 땐 드러나지 않다가 규모가 커지며 나타난 병목.
원인
두 가지가 겹침. ① 스케줄러엔 호출 간 300ms 딜레이가 있었지만 사용자가 직접 트리거하는 getPortfolio()엔 없어, 캐시 미스마다 KIS를 지연 없이 연속 호출 → 자산 수에 비례해 순간 호출이 초당 제한 초과. ② Redis TTL(10초)이 스케줄러가 자산 50개를 300ms씩 순회하는 한 바퀴(15초+, fixedDelay 12초 대기까지 더하면 27초+)보다 짧아, 조회 시점엔 캐시가 대부분 이미 만료돼 매번 KIS를 직접 호출.
해결
① 캐시를 채우는 fetchAndCache 경로에 rate-limit 가드(300ms sleep)를 넣어 미스가 몰려도 초당 제한을 넘지 않게 함 — 캐시 히트 시엔 딜레이가 없어 평소 응답엔 영향 없음. ② 캐시 TTL을 스케줄러 한 바퀴보다 길게 10초 → 30초로 조정해, 백그라운드가 미리 채운 캐시를 조회가 거의 항상 히트하도록 설계.
성과
KIS 직접 호출이 크게 줄고 포트폴리오 조회가 캐시 히트로 안정화. 대신 화면 가격이 최대 30초 늦게 갱신될 수 있어, 실시간성보다 안정성을 택한 의도된 트레이드오프. 추후 실시간성까지 보장할 수 있게 업데이트 예정.
💡 프로젝트 회고 및 배운점

실시간 시세를 얼마나 자주, 어디까지 신뢰할지가 계속 고민이었습니다. 처음엔 매 요청마다 외부 API를 부르면 항상 최신이라고 단순하게 생각했는데, 사용자와 자산이 늘수록 호출량을 감당하지 못한다는 걸 캐시로 흡수하며 배웠습니다. 현재 EC2에 Docker Compose로 배포해 HTTP로 서비스 중이고, 도메인·HTTPS는 아직 붙이지 못했습니다. 다음으로는 WebSocket 연결이 늘 때 브로드캐스트 병목을 부하 테스트로 확인해보려 합니다. 또한 추후에는 완벽한 실시간성까지 보장할 수 있도록 업데이트할 예정입니다.
